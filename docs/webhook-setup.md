# Настройка webhook от Aspro

Этот документ — пошаговый рецепт настройки webhook от Aspro CRM в твоё
приложение. У Aspro вебхуков нет HMAC-подписи, поэтому защита делается
на двух рубежах: секретный токен в URL + общий секрет в заголовке.

## Зачем webhook

Без webhook твоё приложение должно периодически опрашивать Aspro
(автосинк раз в час/сутки) — изменения в Aspro подъезжают с задержкой.
Webhook решает проблему: Aspro сам присылает уведомление при
создании/обновлении ключевых сущностей, и приложение обновляет данные
за 1-2 секунды.

## Какие сущности можно покрывать вебхуком

Aspro поддерживает webhook по большинству ключевых моделей:

| Модель | Действия | Типовое назначение |
|--------|----------|---------------------|
| `transaction_pls` | create / update | П&У-транзакции |
| `plan_money` | create / update | Плановые платежи |
| `transaction` | create / update | ДДС / факт-платежи |
| `act` | create / update | Акты выполненных работ |
| `client` | create / update | Клиенты |
| `crm/deal` | create / update | Сделки |

(Полный список доступных событий — см. в админке Aspro раздел
«Интеграции → Webhooks».)

## Архитектура защиты — два рубежа

У Aspro нет HMAC-подписи запроса. Делаем безопасность так:

### Рубеж 1 — per-tenant токен в URL

Сгенерируй случайный 32-байтный токен для каждой компании-клиента
(если у тебя multi-tenant) или один токен для своей инсталляции (если
single-tenant). Положи в БД компании. Поставь в URL вебхука:

```
https://<твой-домен>/api/aspro/webhook/<token>
```

Запросы без правильного токена → 404. URL и есть «секрет первого уровня».

### Рубеж 2 — общий секрет в заголовке

В Aspro есть «Custom Headers» в настройках вебхука. Добавь свой:

```
X-Aspro-Secret: <случайная-длинная-строка>
```

На стороне приёмника:

```python
expected = os.environ['ASPRO_WEBHOOK_SECRET']
if request.headers.get('X-Aspro-Secret') != expected:
    return jsonify({'error': 'forbidden'}), 403
```

Сгенерировать секрет: `openssl rand -base64 32`.

**Оба рубежа обязательны** — если секрет не задан, можно случайно
выкатить публичный эндпоинт.

## Шаги настройки

### Шаг 1 — приготовить URL и секрет на своей стороне

1. Сгенерируй per-tenant токен (32 байта случайных), сохрани в БД.
2. Задай `ASPRO_WEBHOOK_SECRET` в окружении сервиса (env-переменная
   на твоём хостинге или собственном сервере, или в secrets manager).
3. Подними endpoint `POST /api/aspro/webhook/<token>` который:
   - проверяет токен (если не найден → 404),
   - проверяет заголовок `X-Aspro-Secret` (если не совпал → 403),
   - читает body (JSON), обрабатывает событие,
   - **отвечает 200 как можно быстрее** (Aspro считает retry по таймауту).

### Шаг 2 — добавить webhook в Aspro

В админке Aspro: **Настройки → Интеграции → Webhooks → Добавить**.

| Поле | Значение |
|------|----------|
| URL | `https://<твой-домен>/api/aspro/webhook/<token>` |
| Метод | `POST` |
| Custom Headers | `X-Aspro-Secret: <твой_секрет>` |
| Триггеры | модели/действия из таблицы выше — отметь нужные |

Сохрани.

### Шаг 3 — проверить, что работает

1. Создай тестовую сущность в Aspro (например тестовый плановый платёж).
2. Проверь логи своего приложения — должна быть запись POST с 200 от
   Aspro.
3. Проверь, что данные обновились в твоей БД.

Если Aspro прислал webhook, а приложение ответило **403** — секрет не
совпал. Проверь:
- В Aspro в Custom Headers имя заголовка точно `X-Aspro-Secret`
  (с дефисами).
- Значение совпадает с `ASPRO_WEBHOOK_SECRET` на сервере (без лишних
  пробелов).

Если Aspro прислал webhook, приложение ответило **200**, но данных нет
— проверь:
- Поле `model` в payload — точно из тех, что ты обрабатываешь?
- Поле `action` — `create`/`update` (или `delete`, если поддерживаешь)?
- Логи на исключения внутри обработчика.

## Что НЕ покрывает webhook

- **Удаление в Aspro** — для некоторых моделей `delete` через webhook
  не присылается стабильно. Рекомендуется периодический reconcile-pass
  раз в сутки, сверяющий список сущностей в Aspro с локальной БД.
- **Массовые операции** — если в Aspro обновили 500 сущностей разом,
  ты получишь 500 вебхуков подряд → твой сервис должен это переварить
  (очередь / batch-обработка).

## Безопасность — итог

- URL содержит секретный per-tenant токен — **первый рубеж**.
- Заголовок `X-Aspro-Secret` — **второй рубеж**. Без него запрос
  отклоняется 403, даже если URL знают.
- Оба значения **никогда не логируй полностью** — попадание в Sentry
  или логи делает их public-readable.
- Логируй только первые 8 символов токена для диагностики:
  `token=abcd1234...`.
